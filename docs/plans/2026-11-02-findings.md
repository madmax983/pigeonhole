# Plan: fix the slot-fleet findings

Source: [`docs/FINDINGS.md`](../FINDINGS.md). The findings are about
autumn-web, so most fixes go to `autumn-foundation/autumn`. Pigeonhole gets
the app-side fixes and the status notes.

## Root causes

| # | Finding | Cause in autumn-web |
| --- | --- | --- |
| 1 | The slow-query log charges a fan-out to `SELECT ?`. | `Db::drop` measures the time from checkout to release. It logs that time as `slow database query` with a fixed `sql = "SELECT ?"`. The census handler holds `Db` across the fan-out. |
| 2 | The boot warning speaks Postgres to a SQLite fleet. | Trunk already selects SQLite advice. But the advice tells you to set `ulimit -n` above the connection count. SQLite uses about `2 × connections + databases` file descriptors. |
| 3 | Slot mode accepts any routing key. | This is correct by design: a slot key never names a file. The guide does not say it. |

## Brainstorm

- F1: give the hold time its own event and message. Drop the `sql` field.
- F1: log each statement, not the hold. The statement timer runs only while
  a query observer is in scope. That change is too large.
- F1: rename the metric key `"<route> SELECT"` too.
- F1, app: use `LazyDb` and check out after the fan-out.
- F2: state the file-descriptor estimate in the warning.
- F2: read `RLIMIT_NOFILE` and compare.
- F2: say that `max_open` is a soft limit.
- F3: one guide line. Point to `TenantDbId::parse`.
- F3: add a `strict_keys` option to slot mode.
- F3, app: prove that every pigeon name is a valid tenant-mode id.

## Reverse brainstorm: how to make it worse

| Make it worse | So we do this |
| --- | --- |
| Keep the word "query" for a hold time. | The new message says "connection held". |
| Keep a fake `sql` field. | The new event has no `sql` field. |
| Remove the hold warning. | Keep it. A long hold is a real problem: it pins a pool slot. |
| Rename the metric key and break dashboards. | Keep the metric key. Write the gap in the PR. |
| Give a file count that ignores the control database. | Count every pool: `2 × connections + databases`. |
| Promise a hard limit. | Say that a burst opens more than `max_open`. |
| Reject keys in slot mode. | Do not. The app owns its key rules. Document the gap. |
| Fix the app with a timing test. | Use a test that blocks on the pool. It has no timer race. |

## Six hats

- **White (facts).** Census: 2,728 files, 6.6 s, one log line. Pigeonhole
  boot: 64 × 2 + 10 = 138 connections. Open files: 64 × 5 = 320 for the
  fleet, plus 2 × 10 + 1 = 21 for control: 341.
- **Red (feel).** An operator sees `SELECT ?` and looks for a query that is not
  in the code. That costs trust in the log.
- **Black (risk).** A log parser that matches "slow database query" stops
  seeing hold events. This is the intent. The changelog says it.
- **Yellow (value).** The logs are correct. The warning gives the right
  number. The guide names the gap before an app meets it.
- **Green (ideas).** Run the hold warning inside the `Db` span, so the log
  shows the pool and the shard. Add a guide line on fan-outs and `LazyDb`.
- **Blue (process).** RED, GREEN, REFACTOR, in each repo. One PR in each. Then
  a review by agents from more than one view.
